## 2026-05-11 — Advisory quick-reply UX fixes + smoke test suite

### Root cause (two bugs)
1. **Frontend buttons didn't submit**: `setCommand(opt)` is async; by the time
   `setTimeout(form.requestSubmit, 0)` fired, `command` state was still stale so
   `handleSubmit` bailed on `!command.trim()`.
2. **"yes, inspect it" → approval gate dead-end**: The approval classifier sent any
   affirmative-prefix phrase to the LLM even when `has_pending_plan=False`.  The LLM
   reliably returned "yes = approval", causing the backend to return "There is no
   pending workflow to approve" for every advisory quick-reply.

### Fix
- `frontend/src/App.tsx`: replaced `setCommand + form.requestSubmit` with direct
  `executeCommand(text)` call; `executeCommand` takes text as a parameter and also
  handles scroll-to-pending automatically.
- `backend/orchestration/approval_classifier.py`: gated both keyword fast-path and LLM
  path behind `has_pending_plan`.  When the session is idle, `is_approval_command`
  returns `False` immediately without any LLM call.

### Regression coverage added
- `tests/unit/backend/test_approval_classifier.py`: updated all tests to reflect
  corrected semantics; added `test_keyword_approvals_return_false_without_pending_plan`
  and `test_ambiguous_phrase_without_pending_plan_returns_false`.
- `tests/integration/test_user_flows.py::TestAdvisoryFollowup`: 7 new tests covering
  the full advisory → quick-reply → normal response path.

### Smoke suite
- `tests/smoke/ec2_smoke.py`: live end-to-end smoke script that hits the real backend.
  Covers: health, session creation, meta question, advisory quick-reply (3 phrases),
  bare "yes" with no pending plan, unknown intent.  Verified 6/6 PASS against EC2.
- `scripts/ec2/update-from-git.sh`: smoke suite runs automatically post-deploy when
  `HELIX_SMOKE_URL` is set.

## 2026-05-11 — Slice A: Persistence contract for a turn

### Root cause
Multiple structural issues caused history, run records, and artifacts to be silently
dropped or misdirected:
1. `_materialize_run_artifacts`, `download_script`, and the script generation helper all
   used `Path(__file__).parent.parent / "sessions"` — a hardcoded path that diverges
   from `history_manager.storage_dir` whenever `HELIX_SESSIONS_DIR` is set.
2. The `execute_plan=True` branch in `/execute` called `build_standard_response` and
   `return CustomJSONResponse(standard)` directly, bypassing `_dispatch_result` and
   never writing a history entry for agent execute_plan turns.
3. The `qa_safe_fallback` path returned a raw `CustomJSONResponse` without going through
   `_dispatch_result`, so advisory/Q&A turns in mock mode also skipped history.

### Fix
- Extracted `_record_turn()` as the single authoritative persistence helper, called from
  `_dispatch_result` (the canonical exit point) and any branch that needs history writes.
- Replaced the inlined persistence block in `_dispatch_result` with a call to `_record_turn`.
- Fixed all three hardcoded `sessions` path references to use `history_manager.storage_dir`.
- Fixed `execute_plan=True` branch to route through `_dispatch_result`.
- Fixed `qa_safe_fallback` branch to route through `_dispatch_result`.
- Fixed `bio_orchestrator._script_path_for()` to use `history_manager.storage_dir`.

### Tests
`tests/unit/backend/test_turn_persistence_contract.py` — 9 cases:
- Scriptable bio tool (bulk_rnaseq_analysis): history+run record written; artifact URIs exist under storage_dir.
- Advisory / handle_natural_command: history entry written; ≤1 run record.
- execute_plan=True path: history entry written (was broken before).
- Multi-turn: N turns → N history entries in same session.

## 2026-05-10 — Remove broad length fallback from tabular analysis planning gate

### Root cause
`is_analytical_request` in `backend/tabular_qa/analysis_planner.py` contained a final
fallback: `return len(c.split()) >= 8`. Any message longer than 8 words on a session
with a tabular upload was classified as an executable analysis request, bypassing the
LLM router entirely. This caused meta/comparative questions ("what's the difference
between your next suggested step and the previous analysis?") to produce a full
`tabular_analysis` plan waiting for approval — the wrong response type.

### Fix
Removed the length fallback. `is_analytical_request` now returns `False` for anything
that does not match the explicit analytical cue keywords. Ambiguous or conversational
turns fall through to the main LLM router, which already has `tabular_qa`,
`handle_natural_command`, and `unknown_intent` available, giving us a real "I don't
know / please clarify" boundary without adding new keyword rules.

### Tests
`tests/unit/backend/test_analysis_planner_gate.py` — 27 cases covering:
- 16 meta/conversational/comparative commands that must NOT trigger the gate
- 10 analytically explicit commands that MUST trigger it
- no-upload guard

## 2026-05-06 — Session `584fce12-7108-4698-a9f0-8826b8dfd1a8`: router ignored in-session Excel

### What happened (EC2 `/opt/helix/sessions/584fce12-…json`)
1. User uploaded `media-5 (2).xlsx` (~2.2 MB); intake and `schema_preview` (tabular,
   sheet `gene_morpheus_mem`, 90×67) succeeded.
2. First command `what can I do with this file?` → `tool=agent` → advisory JSON
   (correct), including a suggested follow-up to profile the workbook.
3. Second command `profile the Excel workbook now` → **`tool=unknown_intent`** with
   `needs_clarification`, claiming no workbook was provided — contradicting the
   session’s `uploaded_files`.

### Root cause
The LLM router (`CommandRouter._route_with_llm`) only saw the bare user text. It did
not receive explicit session upload metadata, so it treated the request as
underspecified and returned `unknown_intent` instead of `tabular_analysis` /
`tabular_qa`.

### Fix
1. **Deterministic pre-route** (`backend/command_router.py`): If the session already
   has a tabular upload and the command matches profiling/inspection verbs plus
   workbook/file language (or “profile/describe it”), route to `tabular_analysis`
   (same path that loads the file and returns schema / dimensions — appropriate
   “profile”).
2. **LLM router hint**: Append a short “Session context: tabular file(s) already
   uploaded …” line to the router user prompt when uploads exist, instructing not to
   use `unknown_intent` for generic “the workbook” follow-ups.
3. **Parameter hygiene**: `_extract_parameters` for tabular tools now prefers
   `local_path` over bare `filename`; `dispatch_tool` tabular handler accepts
   `file_path` as an alias for `data_path` (`backend/main.py`).

### Verification
- Unit test `test_profile_workbook_with_session_xlsx_routes_tabular` in
  `tests/unit/backend/test_tabular_ingest.py`.

## 2026-05-05 — Fix: tabular analysis sandbox import error + history not saved on failure

### Symptoms (session `a189d1b5-362d-49b2-ad69-9c4c9ed11ae0`)
1. User ran a tabular analysis and received no output; session history was blank.
2. EC2 backend logs showed `KeyError: '__import__'` during sandboxed code execution.

### Root cause — Bug 1: `KeyError: '__import__'` opaque error / bad retry
`backend/tabular_qa/executor.py` runs LLM-generated code in a restricted dict-based
builtins environment that deliberately omits `__import__`. When the LLM produced
`import scipy` the sandbox raised `KeyError: '__import__'` — an internal Python
detail that is meaningless to the model. The retry in `analysis_executor.py` appended
that raw error to the END of the prompt, which the model largely ignored.

### Fix — Bug 1
1. **`backend/tabular_qa/executor.py`**: Detect `KeyError: '__import__'` and replace it
   with a human-readable (and LLM-readable) `SandboxImportError` message that names
   the pre-bound variables and explicitly forbids `import` lines.
2. **`backend/tabular_qa/analysis_executor.py`**: On retry, prepend a `CORRECTION
   REQUIRED` preamble that restates the constraint before the analysis goal, so the
   model reads the correction instruction first.

### Root cause — Bug 2: history never saved for tabular analysis path
`main.py` lines 2969-2982 (tabular analysis execution path) called
`return CustomJSONResponse(std)` without ever calling
`history_manager.add_history_entry`. Every other execution path reaches that call
via `_dispatch_result`, but this block was an early-return that bypassed it entirely,
leaving the session history empty regardless of success or failure.

### Fix — Bug 2
Added an explicit `history_manager.add_history_entry(...)` call in the tabular
analysis execution block in `backend/main.py`, immediately before the early
`return CustomJSONResponse(std)`. The call is wrapped in a try/except so a logging
failure can never mask the real result returned to the frontend.

### Files changed
- `backend/tabular_qa/executor.py` — translate `KeyError: '__import__'` → clear message
- `backend/tabular_qa/analysis_executor.py` — prepend error preamble on retry
- `backend/main.py` — write history entry before early return in tabular exec path

## 2026-05-06 — Beta hotfix: `No module named 'duckdb'` on file upload

### Symptom
User uploaded `media-5__2_.xlsx` to https://helix-beta.noricum-biosoft.com/
(session `fd3e53f0-6ad2-4375-b8a5-70fea4535496`) and the backend returned
`No module named 'duckdb'`. Same root cause would have surfaced as
`No module named 'openpyxl'` once duckdb was installed, since the file is
`.xlsx` and `pandas.read_excel` requires openpyxl for that extension.

### Root cause
Deploy-contract gap, not a code bug. `backend/ds_pipeline/pipelines/ingest.py`
imports `duckdb` at file-upload time and uses `pandas.read_excel` (→ openpyxl)
for `.xlsx` inputs. Both deps were declared only in the **root**
`requirements.txt` (lines 26 and 54), but `scripts/ec2/bootstrap-ec2.sh:102`
and `scripts/ec2/update-from-git.sh:25` both `pip install -r backend/requirements.txt`
— so the production `.venv` (a conda env at /opt/helix/.venv, Python 3.11)
never received them. Direct probe on EC2:

```
$ /opt/helix/.venv/bin/python -c "import duckdb"
ModuleNotFoundError: No module named 'duckdb'
$ /opt/helix/.venv/bin/python -c "import openpyxl"
ModuleNotFoundError: No module named 'openpyxl'
```

The split between the two requirements files has existed for a while; the bug
only became user-visible when this user happened to upload an Excel file
(triggering both imports).

### Fix
1. **Source of truth** (`backend/requirements.txt`): added `duckdb>=1.0` and
   `openpyxl>=3.1` under a comment explaining they're required by the
   ds_pipeline tabular-ingest path. This is what bootstrap and
   update-from-git both consume.
2. **Live remediation**: installed both into the running prod venv via
   `aws ssm send-command`:
   `sudo -u helix /opt/helix/.venv/bin/pip install duckdb>=1.0 openpyxl>=3.1`.
   Resolved to `duckdb-1.5.2`, `openpyxl-3.1.5`, `et-xmlfile-2.0.0`.
3. **Restart**: `systemctl restart helix-backend` so the running uvicorn
   process loads the new dependencies. `helix-backend` reports `active`,
   `/health` returns `status: healthy`.
4. **End-to-end replay**: re-ran `ingest_tabular` against the user's exact
   uploaded path
   `/opt/helix/sessions/fd3e53f0-6ad2-4375-b8a5-70fea4535496/uploads/raw/media-5__2_.xlsx`
   on the live backend. Result: 90 rows × 67 cols on sheet `gene_morpheus_mem`
   ingested cleanly.

### Why our existing tests didn't catch this
`tests/unit/backend/test_tabular_ingest.py` already exercises this exact import
path. It passes in dev because the developer venv was bootstrapped from the
root `requirements.txt` (which has duckdb), not from `backend/requirements.txt`.
The gate suites therefore measure the dev environment's deps, not the
production deploy contract. To prevent recurrence we should add a CI step that
provisions a clean venv from `backend/requirements.txt` and asserts
`from backend.main import app` and `from backend.ds_pipeline.pipelines.ingest
import ingest_tabular` both succeed. Tracked as a follow-up
(`backend-deploy-contract-not-tested`, see release_readiness.json blockers).

### Operational note
This is the second deploy-contract gap surfaced against the live beta in 24h
(prior was AL2 having no Node/npm). Both point at the same underlying issue:
the production deploy path is implicitly different from `pytest` on a developer
laptop. The deploy-script scripts assume a contract that's never end-to-end
verified. Recommendation: add a Makefile/CI target that builds a fresh venv
from `backend/requirements.txt` only, then imports the canonical entry points,
and gate releases on it.

## 2026-05-04 — Investigation: "Server: error" on helix-beta.noricum-biosoft.com

### Symptom
The deployed beta UI at `https://helix-beta.noricum-biosoft.com/` shows a red
`Server: error` badge. The frontend never reaches a healthy state, and (by
extension) every other API call from the SPA fails too.

### Root cause
The JS bundle currently served by nginx
(`/assets/index-DnhrdT75.js`) was built with a baked-in
`VITE_API_BASE_URL=http://helix--Publi-7CO3kaz1lrRR-443122446.us-west-1.elb.amazonaws.com`
(visible in the minified bundle as
`Ml=iG("http://helix--Publi-7CO3kaz1lrRR-443122446.us-west-1.elb.amazonaws.com")??""`).

That URL has two fatal problems for a browser loading the page over HTTPS:

1. **Mixed active content** — `axios.get('http://...')` from an `https://` page
   is blocked unconditionally by Chrome/Firefox/Safari, so
   `helixApi.healthCheck()` rejects → `setServerStatus('error')`
   (`frontend/src/App.tsx:305-317`).
2. **Internal AWS hostname** — the ALB DNS name `helix--Publi-...elb.amazonaws.com`
   does not resolve from the public internet (`curl` from outside AWS returns
   `Could not resolve host`), so even without the mixed-content block the
   request would fail.

The backend itself is healthy. Same-origin probing confirms it:

```
$ curl -i https://helix-beta.noricum-biosoft.com/health
HTTP/1.1 200 OK
{"status":"healthy","service":"Helix.AI Bioinformatics API","agent_disabled":false,"mock_mode":false}
```

The EC2 nginx config (`scripts/ec2/nginx-helix.conf.template`) already proxies
`/health`, `/execute`, `/agent`, `/create_session`, `/download`, `/mcp/*`,
`/session/*`, `/jobs/*` to `127.0.0.1:8001`, and the EC2 install/update scripts
(`scripts/ec2/bootstrap-ec2.sh:109`, `scripts/ec2/update-from-git.sh:41`) build
